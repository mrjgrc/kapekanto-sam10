1. Executive summary

What it does. Kapé Kanto Barista is a chat assistant for Kapé Kanto, a small neighbourhood café that we invented for this project. Guests type questions such as “What time do you close on Saturday?”, “How much is an iced Spanish Latte?” or “Can I bring my dog?” and get a short answer taken only from the café’s own documents. It does not take orders, bookings or payments; it explains how to do those things instead.

What was wrong with how it was run. The starting point was the open-source chat app LibreChat running the way it ships: one machine, a database with no backups, no monitoring, nobody told when it breaks, passwords and keys sitting in a settings file, and one shared administrator login for the cloud account.

What we changed. We rebranded it into a café assistant, put it on Amazon Web Services (AWS) behind a secure HTTPS address, and then ran it like a real service: a dashboard and eight alarms that email us, a database backup to storage every 30 minutes with a tested restore, every secret moved into AWS Parameter Store, personal logins with MFA instead of a shared admin, an audit trail (CloudTrail), a monthly budget alert, and scheduled jobs that check the bot every hour by asking it 12 test questions.

What improved. See Results: the system now tells us within minutes when it breaks (it used to tell nobody), we can lose at most 30 minutes of chat history (before: everything), and a full restore takes about a minute.

Live system: https://da9oihrh3ah8y.cloudfront.net E-02

3. Our system and its system card

SYSTEM CARD: Kapé Kanto Barista

1. What it does. Answers guests’ questions about one (fictional) café — menu and prices, opening hours, location, payment, reservations, loyalty card and house rules — using only the café’s own four documents. If the answer is not in them, it says so and gives the café’s contact details.

2. Who uses it, and who must not. Intended users: café guests and new staff looking up house information. Explicitly NOT for: allergy or medical safety decisions, taking orders/bookings/payments, refunds, assessing job applicants, or any decision about an identifiable person.

5. Data. Source: written by us for this project (no licence issues). Size: 4 Markdown files, about 9 KB. Anything personal: no — all invented (café, street, phone, email). Sent to a third-party AI service: the café documents and the guest’s question go to Groq; both are invented/demo data, and the banner tells users not to enter personal data.

6. How good it is. See Results: measured by ops/kk-eval.py, which asks 12 labelled questions every hour (10 answerable, 2 that must be refused or deflected) and checks each answer for the expected fact.

7. How it is served. EC2 t3.small, us-east-1, Docker; public URL above (CloudFront → nginx → LibreChat /api/agents/chat); model llama-3.1-8b-instant on Groq’s free tier. If Groq is down or rate-limits us, the chat shows an error message, the hourly answer test fails and the kk-answers-bad alarm emails us.

8. Limitations and risks. It cannot take orders, bookings or payments, and knows nothing outside its 4 documents. If a document is wrong, the bot repeats the mistake confidently. A small model can occasionally mix up two prices or invent a detail — users must confirm prices at the counter and must always ask staff about allergies. Misuse: people could try to make it talk about other topics (“prompt injection”); the prompt tells it to decline, but this is not guaranteed.

9. Operational summary. Code: our Git repository (see README). Backups: MongoDB dump to S3 every 30 minutes, kept 30 days; S3 versioning on. Health: 8 CloudWatch alarms → SNS email. Contact: the two of us (hello@kapekanto.example for the fictional café).

Trade-off we chose: we optimised for Security and Operational Excellence and deliberately accepted Reliability as weaker: one instance in one Availability Zone is a single point of failure. The gap we would fix first is Reliability — move MongoDB to a managed, multi-AZ database (or Amazon DocumentDB) so that losing the EC2 instance does not lose up to 30 minutes of chats, and put the instance in an Auto Scaling group of one so it is replaced automatically.

Backup and restore (WS-C)

What would have to be restored: (1) the MongoDB database (users, conversations, messages); (2) the S3 content (docs/ café knowledge, deploy/ release); (3) configuration and secrets — the six /kapekanto/* parameters in Parameter Store (CREDS_KEY/CREDS_IV are needed to read stored data); (4) the server itself, rebuilt from the repository with infra.sh + setup.sh.

How: kk-backup.timer runs mongodump every 30 minutes to s3://kapekanto-sam10-752250844846/backups/mongo/; the bucket is versioned and a lifecycle rule keeps backups 30 days (non-current versions 7 days).

RPO / RTO. We can lose at most the last 30 minutes of conversations (RPO = 30 min, one backup interval). Restoring the database from S3 takes about a minute and a full rebuild of the server from the repository about 15 minutes (RTO ≈ 15 min).

Incident: disk full (WS-F) E-15

StepTime (UTC, 19 Nov 2026)Manila time
Fault started — a runaway debug.log grows in /var/log/kapekanto11:15:2619:15
Detected — kk-disk-high went OK → ALARM (disk 96%)11:21:3119:21

Time to detect: 6 min 5 s (limited by the 5-minute health/disk probe). Time to fix: 2 min 31 s after the alarm.

Root cause. The disk filled because a log file in /var/log/kapekanto grew without limit. Our rotation rule capped logs at 50 MB, but the operating system only runs logrotate once a day, so the cap was never checked while the file grew; at 96% MongoDB would soon be unable to write, and logins, new chats and backups would fail.

Fix. truncate -s 0 on the file (keeps the open file handle valid, frees the space immediately) — disk back to 43%.

Prevention. A systemd override (deploy/systemd/logrotate.timer.d/hourly.conf, now in the repository and installed by setup.sh/update.sh) makes logrotate run every hour, so no log can exceed 50 MB for more than an hour; Docker logs are already capped at 3 × 10 MB per container; and the 80% disk alarm stays as the safety net.

RUNBOOK: Root disk filling up (kk-disk-high)

Owner: Kapé Kanto ops (Chris & Jerry) · Last tested: 2026-11-19 · Takes: ~10 minutes · Ask: whoever is on the SNS email list

  1. WHAT THIS IS FOR. Freeing disk space on the Kapé Kanto server and finding what filled it, before MongoDB stops saving chats.
  2. HOW YOU KNOW YOU NEED IT. Email “ALARM: kk-disk-high” (DiskUsedPercent > 80%), or guests say new messages are not saved. Command that shows the problem: 
    aws ssm start-session --target $KK_IID      # no SSH needed
sudo df -h /
  3. WHAT IT AFFECTS. At 100% MongoDB cannot write: logins and new chats fail for every guest; backups fail (kk-backup-missing fires next).
  4. HOW TO DO IT. 
    sudo du -xh / --max-depth=2 2>/dev/null | sort -h | tail -15   # -> the biggest folders
sudo du -sh /var/log/* /var/lib/docker/containers/* | sort -h | tail
sudo ls -lhS /var/log/kapekanto | head                          # -> the runaway file
sudo lsof +L1                                                   # deleted-but-open files still holding space
sudo truncate -s 0 /var/log/kapekanto/<file>                  # keep the inode, free the space
sudo logrotate -f /etc/logrotate.d/kapekanto                    # rotate + compress the rest
sudo df -h /                                                    # -> back under 50%
  5. HOW TO CHECK IT WORKED.
    • ☐ df -h / under 80% and the alarm returns to OK within 10 minutes
    • ☐ ask the test question “What time do you close on Saturday?” and get “11:00 PM”
    • ☐ sudo systemctl start kk-backup then tail /var/log/kapekanto-ops.log shows [backup] ok
    • ☐ no new alarms for 10 minutes
  6. HOW TO UNDO IT. Nothing to undo for truncating logs. If you deleted the wrong file, restore it from the newest backup (sudo /opt/kapekanto/repo/ops/kk-restore-test.sh shows the procedure) or rebuild with update.sh.
  7. GOTCHAS. rm on a file a process still has open does not free space (use truncate or restart the process; check lsof +L1). Docker container logs live under /var/lib/docker/containers, not /var/log. The disk metric is published every 5 minutes, so the alarm can lag by up to 10.
  8. CHANGE HISTORY. 2026-11-19 — written after the disk-full incident; prevention: hourly logrotate with a 50 MB size cap, Docker log limits, disk alarm at 80%.

8. Results

9. What we would do next

  1. Managed, multi-AZ database (or DocumentDB) and an Auto Scaling group of one — removes the single point of failure (our first Reliability gap).
  2. Custom domain with ACM certificate and AWS WAF rate limiting on CloudFront to protect the free-tier model quota from abuse.
  3. Deploy from the repository automatically (GitHub Actions → upload release to S3 → SSM Run Command update.sh).
  4. A bigger evaluation: 30+ labelled questions including Filipino/Taglish phrasing, run nightly, with the pass rate shown on the dashboard.
  5. Guest feedback button stored in MongoDB and a weekly SNS summary of thumbs-down answers.
